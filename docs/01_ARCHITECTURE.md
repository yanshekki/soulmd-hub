# SoulMD Hub: Enterprise Architecture Overview

## 1. System Paradigm
SoulMD Hub operates on a **V5 Web2.5 Hybrid AgentFi Architecture**. It bridges traditional Web2 user experiences (email/password, sessions, fast relational databases) with Web3 decentralized asset ownership (NEAR Protocol NFTs, Token-Gating, Ed25519 Cryptographic Authentication). 

The system is designed to be highly scalable, stateless at the AI routing layer, and strictly guarded against unauthorized access via physical cryptographic verification.

## 2. Core Tech Stack
* **Frontend:** Vanilla JavaScript, HTML5, TailwindCSS (Utility-first styling), Near-API-JS (for Browser LocalStorage KeyStore management and Ed25519 payload generation).
* **Backend Controller:** PHP 8+ (Stateless RESTful APIs, PDO for secure database interactions, Libsodium for cryptographic verifications).
* **Database:** MySQL (InnoDB) with a highly normalized, unified schema.
* **AI Integrations:** DeepSeek (Primary Official Text Engine), Together AI (Primary Vision Engine Llama-3.2), and OpenAI-compatible proxy routing for Bring-Your-Own-Key (BYOK) users.
* **Blockchain Network:** NEAR Protocol (Mainnet).

## 3. High-Level Component Topology

### 3.1. Dual-Track Routing Engine (`api/chat.php` & `api/self-chat.php`)
The platform implements a dual-track AI execution layer:
* **Official Gateway (`chat.php`):** Subject to strict daily limits, paywall intercepts, and platform-managed API keys. It handles tier-based capabilities (Free/VIP/PRO).
* **BYOK Proxy Gateway (`self-chat.php`):** A stateless proxy that utilizes user-provided, AES-256-CBC encrypted API keys stored in the database. It bypasses platform rate limits but strictly enforces Web3 Token-Gating for NFT-based AI agents.

### 3.2. Multiplayer Delta Sync & Presence
To support collaborative interactions with AI agents, the platform utilizes a **Short-Polling Heartbeat mechanism**:
* Clients periodically ping `/api/chat-sync.php` every 3.5 seconds.
* The system maintains a lightweight `chat_presence` table to track active participants using unique identifiers (Session + User/Guest ID).
* Only incremental updates (messages with an ID greater than the client's local `lastMessageId`) are fetched and broadcasted to connected users, minimizing database load.

### 3.3. Web3 Authentication Service (`NearAuthService`)
Instead of relying on insecure payload assertions, the backend physically verifies wallet ownership:
1.  The frontend generates a timestamped payload and signs it using the session's Ed25519 private key via `near-api-js`.
2.  The PHP backend validates the detached signature via `libsodium`.
3.  The backend cross-references the public key against the NEAR blockchain via RPC view calls to ensure the key is legally authorized under the claimed `account_id`.

## 4. Grand Unified Schema (Database Overview)
The MySQL schema is heavily indexed for high-concurrency environments. Key entities include:

* **`users`**: Manages Web2 identity, subscription tiers, and permanent mapping to `near_wallet_address`.
* **`souls`**: The core AI agent configurations (Prompts, Modular JSON architectures). Contains `is_nft`, `nft_hash`, and `nft_owner_wallet` to track on-chain asset validity.
* **`chat_sessions` & `chat_messages`**: Tracks conversation threads. Messages include `sender_name` to differentiate users, guests, and the AI Assistant in multiplayer scenarios.
* **`chat_memory`**: Stores sliding-window compressed contextual summaries generated by the AI to preserve context without blowing up token limits.
* **`chat_presence`**: Highly volatile table used exclusively for tracking real-time user heartbeats in shared chat sessions.
* **`user_llm_settings`**: Stores encrypted BYOK credentials and custom fallback routing endpoints.

## 5. Security Posture
* **Anti-Twin Wallet:** The database strictly enforces 1-to-1 mapping. A Web3 wallet cannot be bound to multiple Web2 accounts.
* **Session Pollution Protection:** Only the creator of a session can alter its privacy state (`is_private`). Private sessions instantly block unauthorized read/write attempts.
* **DoS & Injection Resilience:** All `session_token` identifiers are strictly checked against regex patterns (`^[a-zA-Z0-9_-]{8,128}$`) before any database evaluation.
