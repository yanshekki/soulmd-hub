## 2. Web3 Cryptographic Authentication (Ed25519)

### 2.1. The Vulnerability Addressed
In typical Web3 integrations, a naive backend might blindly trust a client-provided `wallet_address`. This creates a severe Identity Spoofing vulnerability where an attacker can impersonate any wallet via simple API payload manipulation.

### 2.2. The SoulMD Hub Solution
SoulMD Hub enforces a strict **Cryptographic Challenge-Response mechanism**:

1. **Payload Generation (Frontend):** Using `near-api-js`, the client retrieves the session private key (authorized by the user's cold wallet/MyNearWallet) from `LocalStorage`. It signs a timestamped message (`soulmd_auth:<timestamp>`) to generate an Ed25519 signature.
2. **Physical Verification (Backend):**
   The `/api/bind-wallet.php` and `/api/wallet-login.php` endpoints receive the payload. The `NearAuthService` utilizes PHP's native `libsodium` extension (`sodium_crypto_sign_verify_detached`) to mathematically prove that the signature was generated by the corresponding private key.
3. **Blockchain Access Key Confirmation (RPC):**
   A valid signature is not enough; the backend queries the NEAR blockchain via RPC (`view_access_key_list`) to guarantee that the `public_key` used for signing is currently an active, legally authorized key attached to the provided `account_id`.

### 2.3. Anti-Twin Vulnerability Guard
To prevent a malicious actor from binding a heavily funded or highly reputed Web3 wallet to multiple Web2 spam accounts, the database enforces a strict `UNIQUE` constraint on the `near_wallet_address` column in the `users` table.

## 3. AgentFi & Token-Gating (NFT Ownership)

AI Agents created on SoulMD Hub can be minted as on-chain assets (NFTs) using the `is_nft` flag. When an agent is tokenized, it falls under the jurisdiction of the **AgentFi Token-Gating** protocol.

### 3.1. Ownership Verification Flow
When a user attempts to chat with an NFT-gated agent via `/api/chat.php` or `/api/self-chat.php`:
1. **RPC View Call:** The `NearRpcService` executes a cross-chain query to the designated Smart Contract (`NEAR_CONTRACT_ID`), calling the `get_soul` method with the agent's `token_id`.
2. **Access Evaluation:** The system evaluates the caller's bound Web3 wallet against the returned blockchain data. Access is granted if:
   * The user is the absolute `owner_id`.
   * The user is listed in the `renters` mapping, and their rental `expiry` timestamp (in nanoseconds) is greater than the current time.

### 3.2. Data Integrity Interception
To protect renters from malicious creators who might alter the AI's core instructions after a rental agreement is formed, SoulMD Hub checks the **Integrity Hash**.
* The server calculates a SHA-256 hash of the agent's `content` and a cryptographic `nft_salt`.
* This hash is compared against the `extra` metadata field returned by the blockchain.
* If a mismatch occurs, the AI Engine halts execution and returns a `Security Interception` alert, preserving the integrity of the traded asset.

## 4. Web2 Security Posture

### 4.1. CSRF (Cross-Site Request Forgery) Protection
All state-changing endpoints originating from the browser interface require a dual-validation CSRF token.
* A cryptographic token is generated and stored in `$_SESSION['chat_csrf_token']`.
* It is injected into the DOM as a global JavaScript variable.
* All `fetch` requests must include this token in the `X-CSRF-Token` HTTP header. `hash_equals()` is used on the backend to prevent timing attacks during comparison.

### 4.2. IDOR (Insecure Direct Object Reference) Prevention
Session boundaries are strictly isolated. The `chat_sessions` table definitively maps a `session_token` to a specific `user_id`.
* **Private Sessions:** If `is_private = 1`, the API instantly rejects read/write attempts from any `user_id` that does not match the session creator.
* **Public Sessions:** Read access is granted globally, and write access is permitted to facilitate the Multiplayer Sync feature, but system administrative actions (like changing privacy states) are strictly locked to the owner.

### 4.3. DoS & Payload Formatting Guards
* **Regex Filtering:** `session_token` inputs are sanitized using strict regular expressions (`/^[a-zA-Z0-9_-]{8,128}$/`) to prevent SQL injection and memory overflow (OOM) attacks from artificially bloated payloads.
* **Input Truncation:** Chat inputs are hard-capped based on the user's `tier` configuration.
